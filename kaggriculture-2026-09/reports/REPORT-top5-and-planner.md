## 3. 市场层:三个发现 + 一个已提交的改动

### 发现 A:收入的 38% 方差来自城镇商店组合,不是我们的操作

同样 agent、同样支出,收入 129,573 vs 179,874(见 REPORT-ongoing-crop-gap.md 第 10 节)。

### 发现 B:价格是"悬崖"不是"斜坡"

商店每 4 步只抽固定数量(单品店 ×2),两个玩家共享同一个池子:
**产量之和 > 抽走量 → 库存无界累积 → 价格砸到地板**。实测终局价:
WOOL **1**(基准 200)、FERTILIZER **1**(基准 100)、MELON 120(250),
而 MILK 常常 243(160,高于基准)。

### 发现 C:原版 router 只在 day6 看"前两家店"查表,之后永不重估


## 4. 磁带的动物/饲料/棚容是"紧耦合均衡"——动一处就崩

想让磁带学榜 1 不养羊,只改市场订单(不碰编排):

| 变体 | 每局钱包差 |
|---|---|
| 去掉全部 `BUY_ANIMAL SHEEP`(保留饲料采购) | **−75,360** |
| 再去掉 `BUY_PRODUCT WHEAT`(以为省饲料) | **−99,827** |

原因:羊不在了但磁带仍按 17 只动物买小麦 → **小麦堆满棚子(容量 100)→ `room_guard` 挡住掉落**;
而把小麦采购也去掉 → 牛直接饿死逃跑(连续两天没喂)。⇒ 动物组合不能靠改订单切换,
必须连饲料/棚容/编排一起重算,这正是"从零生成磁带"要解决的问题。

## 5. 从零开始的规划器:`scripts/planner.py`(脚手架,未达标)

设计:每回合从 observation 读真实状态(位置/地块/库存),按日重建任务表
(收获 → 补种 → 施肥 → 浇水 → 喂食 → 照料 → 收肥),用最近邻把任务派给各只手;
市场订单按"当天工作量的 1/22"雇人(斐波那契前置,前 6 只手只要 20 币/天,第 10 只 89、
第 11 只 144),作物按商店抽走量选。

已修掉四个真实 bug:
1. 观察里的手数滞后一回合 → 每回合都雇人,21 人/天烧光现金(改成本地计数);
2. 任务在 hour 0 分配,而当天的手还没雇 → 只有农夫有任务,其余全 PASS;
3. 每 4 小时重规划会把正在走路的单位重新派单 → 来回空转(改成保留当前任务);
4. 作物配额按"站立数"而非"补种速率"。

现状(seed 900 自对自):reward **2,416**,种 69、收 47、PASS 2,308 —— 与磁带的 ~99,000 差 40 倍。
卡点:**收入陷入低水平均衡**(钱一直停在 2,400,买不起 3,000 的地,只有 3-4 只手、8-10 茬作物)。
下一步要做的是"先有农场设计(哪块地种什么、多少畜舍、多少只手),再让规划器执行",
而不是现在这种"看到空地就种"的被动规划。

**差距的三条根因(都是经济政策,不是调度 bug)**:

⇒ 规划器 v2 要改的是**投资政策**:day 0 就把 25 块地种满、day 3 起买牛/建畜舍、
前 6 只手几乎免费(1+1+2+3+5+8 = 20 币/天)所以早期就该多雇,
而不是像现在这样把现金当目标函数守着。

## 10. 运营层重大发现:公开分是"评分",换提交就重置

`data/leaderboard.json` 刷新后:

* 我们显示 **2,520.0**,时间戳正是 router3 提交的时刻(09-15 15:18);而 09-14 提交的 V42 baseline
  曾达 **2,681.9** —— 说明**公开分 = 当前跟踪提交的评分,旧提交被替换后停止对局,分随之消失**。
* 榜 1 今天从 3,227.2 → 3,150.8,榜前 5 也换了人(Artem The Farmer 3,149.2 冒上来),
  ⇒ **评分本身有 ±5% 的波动,并且需要数小时的对局才收敛**。

**结论:每次提交都是一次至少 12 小时才能读数的实验;频繁提交会让分数一直停在"未收敛的低位"。**
这也是过去几十次提交分数在 2,242–2,702 之间乱跳的重要原因 —— 不全是"本地指标不能预测梯子",
还有"每次换提交都要重新收敛"。**策略:一天最多换一次,并把最有把握的版本留到当天最后一次提交。**

## 13. 规划器动物链:语义全部修对,但经济链仍然打不通

本轮把动物链上剩下的语义错误全部定位并修复(都有实测证据):

| bug | 现象 | 修法 |
|---|---|---|
| `BUILD_*` 当成市场订单 | structs 恒为 0 | 改成工人任务(BUILD_PASTURE/BUILD_COOP) |
| `PLACE` 前不取货 | PLACE 执行 83 次、动物 0 | 插入 PICKUP_AT(先去棚子取动物) |
| **重规划丢弃合成任务** | PLACE 连续 20+ 天挂在任务池里却永远走不完 | `keep` 逻辑保留 PICKUP_AT/RELOAD 这类合成后续任务 |
| 卖出逻辑把动物当商品 | 买 401/卖 400 死循环 | 卖出白名单排除 ANIMAL |

修完后动物终于能被放置并服役(PLACE 11、PICKUP 38、FEED/CARE 各 1),但:

* 一旦投资动物(5 头牛 = 2,000 币),**作物经济立刻崩**(现金降到 42–365),
  接着牛因为没饲料逃跑(动物数回到 0)—— 引擎里"连续两天没喂就逃跑",
  而饲料来自小麦,小麦又需要现金和劳力;
* 12 组配置测下来,**最好的一档是"不养动物"**(自对自 6,066 / 对 V42 7,336)。

⇒ 规划器的下一个真正难点不是 bug,而是**经济调度**:必须让"作物现金流 → 买牛 → 种饲料麦 → 施肥 → 收奶"
这条链在同一套劳力预算里闭环。这已经超出本次会话可完成的范围,已在报告里留档为后续工作。

## 17. PPO 训练已开跑(CPU,104 核远程机)

### 17.1 CPU vs GPU:这个任务上 GPU 只有 1.05×
实测(远程):纯引擎 **692 步/秒/核**;加磁带行为策略 **120 步/秒/核**(agent 逻辑比引擎贵 5.8 倍);
策略网络 2×256 MLP 在 CPU 上 **857,000 样本/秒**(批 4096 = 4.8 毫秒)。
⇒ 一个 200 万步的 PPO 迭代:rollout 0.05 h、更新 0.0026 h(CPU)/0.0003 h(GPU),
**GPU 只快 5%**,因为墙钟 99% 花在 GPU 无法加速的 Python 引擎+agent 上,且网络比数据生成便宜两个数量级。
(真正能提速的是"把策略做便宜 + 多核",不是 GPU;GPU 只有在把网络放大到千万参数、或把引擎
向量化重写时才有意义。)

### 17.2 训练循环里挖出的三个 bug(都已修,均有实测证据)
1. **GAE 递推写错 → 优势指数发散**:我把 `A_{t+1}` 当成了 `V_{t+1}`,递推系数变成
   γ(1+λ)=1.949>1,719 步后溢出成 inf,所有 minibatch 因非有限损失被跳过
   (日志:`ret inf, adv nan, skipped 4`)。改成标准式后 max|adv|=55.5 且有限。
   —— 用合成数组单测 30 秒就复现了,比在训练里猜快得多。
2. **初始策略先验太弱**:不覆盖的动作偏置只给 +2.0 ⇒ 约 10 个候选下 P(不覆盖)=42%,
   覆盖率 61%、钱包崩到 2,015。改成 +6.0 ⇒ P(不覆盖)≈97.6%,钱包回到 100,090。
3. **torch 线程风暴**:96 个 worker × torch 默认线程数 = 上万线程抢 104 核,
   load average 冲到 **1,198**、一轮都跑不完。改为每进程 `torch.set_num_threads(1)`
   + `OMP_NUM_THREADS=1` 后 load 降到 ~100(健康)。

### 17.3 当前配置与首轮实测
残差动作空间(磁带行为策略 + 单步覆盖),奖励 = 逐回合钱包增量(×1e-3),
对手池每轮轮换 v40/v38/v39/v41/aurax7-v5,每次 checkpoint 保存。

```
iter 0 | vs v40 | games 1,408 | steps 1,012,352 | mean wallet 104,333
       | override rate 4.8% | rollout 216.4s update 57.7s | pi -0.0558 v 1.1 ent 0.497 skipped 0
```
⇒ 约 **1M 步/4.6 分钟**(rollout 216s + 更新 58s),200 轮 ≈ 15 小时;
起点策略≈生产磁带(钱包 104,333、覆盖率 4.8%)。

### 17.4 验收纪律(沿用本会话的教训)
训练完或中途的 checkpoint 一律用 `scripts/rl_agent.py` 在**留出城镇 + 对手池**上与

## 18. RL 训练的实际结论:基础设施全通,但**残差动作空间几乎没有油水**

### 18.1 三处训练循环 bug(已修,均有实测)
1. **GAE 递推错** → 优势指数发散(系数 γ(1+λ)=1.949>1),`ret inf / adv nan / skipped 4`,所有更新被跳过。
2. **初始先验太弱**(不覆盖偏置 +2.0 ⇒ P(不覆盖)=42%)→ 覆盖率 61%、钱包崩到 2,015;改 +6.0 后恢复 100,090。
3. **torch 线程风暴**(96 worker × 默认线程数)→ load average 1,198;单线程 + `OMP_NUM_THREADS=1` 后 ~100。
另加**跨轮可比标尺**(固定 6 个 worker 打同一对手/同批种子),才让"崩溃"当场暴露 —— 否则轮换对手的均值根本不可比。

### 18.2 三处动作空间 bug:每一次都用实验定量证明
| 覆盖类型 | 实测代价 | 结论 |
|---|---|---|
| 让单位**改道**走向作物 | 覆盖率 4%→11% 就掉 **97,000** | 磁带是"脚本",移动是相对的 → 全删 |
| **未成熟就收获**(`yield_units>0` 即允许) | 440 次早期收割 → 83,480 **→ 0** | 按"窗口末尾"门控后才 −34 |
| **市场类覆盖**(抛售整堆 / 雇人) | 随机覆盖 **−76k ~ −98k** | 抛售砸垮共享市场价 → 全删 |
| 就地浇水 / 照料 | **±0**(磁带当天本来就会做) | 安全但也无用 |
| 就地收肥 | −59 | 安全、微负 |
| 喂食 | −1,699 / 3 局 | 纯耗饲料 → 删 |

最终**安全配置 = 只在磁带自身 PASS 的回合覆盖 + 无市场动作**:随机覆盖 50% 的代价仅 **−80**(6 局均值,0.08%)✓ 不再破坏。

### 18.3 但安全空间的油水几乎为零(这是关键量化)
* 只有 **94/719 = 13.1%** 的回合存在真实选择;
* 而且这些回合里可用的动作(就地浇水/照料/收肥)恰好是**磁带当天本来就会做的**(实测 ±0),
  有真实后果的动作(市场抛售、雇人、改道)全部是破坏性的(−60k ~ −100k)。

⇒ **PPO 在这个空间里最优解就是"永远不覆盖",即复现磁带**。继续烧算力没有意义。

### 18.4 真正有油水的两个 RL 形态(供后续选择)
1. **市场层**(本会话数据都指向这里:同一 agent 收入差 38%、53k 级别的对局差异、价格悬崖):
   需要重新设计**非破坏性**的市场动作(例如"棚内某货超过阈值时只卖 N 个""雇人上限 +1"),
   而不是现在这种"整堆抛售"。
2. **闭环执行器上的任务分配**(用 planner 的 executor 取代磁带脚本,策略学"派谁去干什么"):
   架构上sound(随时从 observation 重算位置,不存在脚本错位),但起点只有磁带的 ~5%,是数天工程。

## 19. RL 走对了空间:市场层(择时加量抛售)

### 19.1 为什么单位级空间被彻底放弃
单位级覆盖要么**无用**(就地浇水/照料实测 ±0 —— 磁带当天本来就会做),要么**破坏性**:
改道 −97,000、未熟早收 83,480→0。安全子集只有 13.1% 的回合有真实选择,且能选的动作都没油水
⇒ 该空间的最优解就是"永不覆盖"。

### 19.2 市场动作的逐项安全测试(每项"总是执行",3 个种子)
| 动作 | 均值 |
|---|---|
| 只卖一半(**holding**) | **−52,745** ✗(棚容 100 被堵死,磁带自己的计划停摆) |
| 完全不卖 | **−94,683** ✗ |
| **多卖 25% / 50% / 100%** | **−529 / −809(≈中性,略负)** ✓ |
| 多雇 1 人 | **−93,345** ✗(每步都加 → 一天雇 700 人,fib 成本爆炸) |
| 少雇 1 人 | **−65,956** ✗(手槽映射错位,磁带的手部动作落到别的活人身上) |

⇒ **唯一安全的动作是"加量抛售"**;动作空间 = {keep, ×1.25, ×1.5, ×2.0}。

### 19.3 关键正向信号:磁带卖得太保守
随机 50% 加量抛售(6 局):**+321 / +627 / −1,619 / +621 / +29 / +580,均值 +93** ——
5/6 局为正 ⇒ "在合适时机多卖"确实能拿钱。这正是可学的择时问题。

### 19.4 已启动的训练
`--space market`,88 worker × 16 局/轮,300 轮,每轮轮换对手 + 固定标尺:
```
iter 0 | YARDSTICK 151,122 @0.5% | rollout 28.0s update 0.7s | skipped 0   (smoke, 4 workers)
```
起点 = 覆盖率 0.5%(几乎纯磁带),即 PPO 必须自己发现"何时该多卖";
验收仍按纪律:用 `scripts/rl_agent.py` 在**留出城镇 + 对手池**上与磁带逐局配对。

## 20. RL 最终验收:市场层策略**没有超过磁带**(实测判定)

### 20.1 训练过程指标(33 轮,88 进程 × 1,336 局/轮 ≈ 96 万步/轮)
| 迭代 | 固定标尺(24 局,可比) | 覆盖率 | 熵 | pi | v | rollout/update |
|---|---|---|---|---|---|---|
| 0 | 147,125 | 16.4% | 0.429 | −0.0056 | 2.4 | 214/63 s |
| 5 | 150,234 | 17.2% | 0.382 | −0.0042 | 0.9 | 219/64 s |
| 23(峰值) | **150,415** | 19.9% | 0.307 | −0.0025 | 3.4 | 225/61 s |
| 32 | 149,777 | 19.6% | 0.289 | −0.0006 | 4.1 | 220/64 s |

* 吞吐 **≈ 96 万步 / 4.7 分钟 = 1,230 万步/小时**;`skipped 0`(GAE 修复后全程无 NaN)。
* 对照:**纯磁带在同一标尺上 = 151,187** ⇒ 策略从未超过磁带,始终低 ~0.5–1%。

### 20.2 配对验收(决定性)
```
100 个留出城镇 × {RL 策略, 纯磁带} 对同一对手 v40,逐局配对:
mean delta -1,079   t=-1.01   wins 42/100   median -276
```
(20 局样本时曾显示 +2,647 / t=1.15 —— 被 3 个离群大赢撑起,扩到 100 局后消失。)

### 20.3 为什么必然如此(先验就算得出来)
加量抛售的**随机**收益只有 **+93(0.06%)**,而 PPO 要探索就必须维持 ~19% 的覆盖率,
其成本本身就大于这个上限 ⇒ 该空间不存在可学的净收益。

### 20.4 本会话 RL 线的总结论
| 空间 | 实测 | 判定 |
|---|---|---|
| 单位级覆盖(浇水/收获/照料/收肥) | 安全子集仅 13.1% 回合有意义,且可用动作实测 ±0 | **无油水** |
| 单位级覆盖(改道 / 未熟早收) | −97,000 / 83,480→0 | **破坏性** |
| 市场级:holding / hire | −52,745 / −93,345 / −65,956 | **破坏性** |
| 市场级:加量抛售 | 随机 +93(0.06%);训练 3,300 万步后 100 局配对 **−1,079** | **无净收益** |

⇒ **磁带家族是一个很强的局部最优,残差 RL 在它之上没有可测的提升空间。**
要再有提升只有两条路:① 换架构(闭环执行器 + 任务分配策略,起点只有磁带 ~5%,数天工程);
② 以更强的公开磁带为起点(用户已明确不走抄袭路线)。
